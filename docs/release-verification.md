# Single-host release verification

The supported release target is one Windows host with native PostgreSQL 18, Java 24 and Node 22, accessed by browsers on a shared LAN. The private engine stays on loopback. Redis/multi-node routing is outside this release target; its separate historical tests do not establish multi-node session availability.

Run `ops/verify/release.ps1` from PowerShell 7. It reads the ignored backend environment file, or a private `-SettingsPath`, without printing credentials. The test guard checks the actual database name is `collaborative_workspace_test` and distinct from development before writes. The native recovery drill creates and stops its own isolated cluster; it never restores over development. `-SkipInstall` reuses installed locked dependencies. `-SkipRecovery` produces an explicitly partial result rather than a release pass.

The script serializes its phases and retains unique logs/results under `backend/target/release-<id>`. It runs engine validation, the frontend build, the canonical Java/browser tests with search indexing enabled and 500 structural edits, then packaging and actual browser/database restore verification. It checks the current Maven run's summary instead of aggregating stale XML reports. Failed attempts remain failed artifacts. Do not run other recovery/load experiments alongside this workload.

The declared workload covers small bounded documents; supported rich nodes are paragraphs, headings 1–3, bold, italic and both list types. The test matrix includes two independent rich browsers, concurrent/offline edits, 500 serialized heading toggles, committed-result verification from a new browser, indexed search catch-up, 22-member management pagination, 16 paced plain-text peers, overload refusal/recovery, viewer/revoked/outsider denial, named revision restore and local-draft quarantine. This does not claim unrestricted document size, arbitrary concurrent users or an Internet deployment.

Existing safeguards remain: 8 KiB individual updates, 64 KiB rich checkpoints, finite text/node/depth limits, 32 pending client updates, 32 peers/document/instance, eight sockets/user and 256/instance, two isolated worker slots with deadlines. A successful merge is not a saved edit until Java commits it. Busy work must retain stable IDs/pending drafts and recover without a false save. Server acceptance latency summaries are scoped to the browser group, include retries/denial scenarios, and are not network round-trip or load-generator percentiles.

The pre-upgrade combined run failed after 45/80 structural edits with indexing and concurrent recovery/resource contention; an isolated rerun accepted 80. Batch C accepted 500/500 without indexing and observed one recovered engine-unavailable attempt elsewhere in the browser group. Keep both observations. Batch D must record its own controlled combined run before declaring that workload passed.

The local default launcher retains rich disabled until the supported LAN configuration and operation checks in Batch E are ready. Test success alone does not install certificates, account provisioning, scheduled backups, monitoring or a host-loss backup destination.

GitHub's `Build and unit checks` workflow uses pinned action commits and read-only repository permissions. It builds the frontend, runs all private-engine checks and runs non-database Java checks on Ubuntu with Java 24 / Node 22.17.0. Native database/browser/load suites are explicitly disabled there; their skips must not be described as release acceptance. The full Windows/native matrix is the separate release script above, with its unique evidence artifact. No private settings or recovery archives are uploaded by CI.
